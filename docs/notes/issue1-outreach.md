### Path B — GitHub issue as the invitation (recommended for #1)

The independent-verifier ask does not need email at all. A public issue
on our own repo is:

- permanent (an email scrolls away)
- answerable asynchronously (no pressure to reply)
- visible to anyone else who might take it up — the second verifier we
  need may be someone we never thought to ask
- honest by construction: the invitation, the standard, and the
  exit criteria are all in one place

`docs/verifier-onboarding.md` is already the kit; the issue just needs
to point at it.

### Path C — when email surfaces

If the authors' emails become findable (they usually do once the papers
are indexed by Semantic Scholar / DBLP, typically weeks not months),
`docs/notes/issue1-outreach.md` has the ready-to-send text.

## Recommendation

Do not chase the two new authors by email. It costs social capital on a
low-probability path. Write the issue instead — it is strictly better
for #1's actual goal, which is a second implementation, not a specific
person.
